What this is

Orchestra is a local Hermes + OpenClaw coding-agent skill that organizes software the way traditional systems organize meaning — Tree of Life, alchemy, runes, planetary spheres, I Ching, Solomonic ranks, Peircean signs, Numogram, sacred geometry, Enochian, Chaos Magic.

1. Scaffold

Emit dual-named project skeletons (mechanical + symbolic) from a chosen map, with provenance.

2. Diagram

Write HTML, JSON, and Mermaid architecture graphs next to the skeleton or analysis.

3. Analyze → optimize

Observe import graphs, map when the fit is honest, plan renames — write only with --confirm.

Not a network service, magic runtime, or silent auto-refactorer. Weak or forced mappings fail closed. You stay in control of filesystem changes.

Python best case — structure that optimizes the code

Choosing Tree of Life is not a rename game. The map becomes the control plane: each mechanical stage is allowed only the work of its locus. Hermes route: emit → scaffold, then implement domain logic inside each stage’s contract (see examples/python-tree-of-life-pipeline/).

Before — flat code (not optimized)
# myapp/ — mixed responsibilities
utils.py / helpers.py / stuff.py / main.py

# main.py — intake, scoring, and I/O tangled
from utils import load
from helpers import score
from stuff import dump

def run(src):
    data = load(src)       # no contract
    out = score(data)      # scoring knows about files?
    dump(out)              # store? emit? both?
    return out

# Hard to test, hard to map, easy to invent
# WEAK/FORCED correspondences later.
After — optimized by the map
# tol/pipeline.py — one-way flow along the Tree
from .intent import accept     # kether — contract only
from .intake import pull       # chokmah — raw force only
from .analyze import score     # hod — analysis only
from .store import persist     # yesod — foundation only
from .output import emit       # malkuth — manifestation only

def run(source: str, *, max_items: int = 12):
    intent = accept(source, max_items=max_items)
    raw    = pull(intent)           # no scoring here
    scored = score(intent, raw)     # no file I/O here
    saved  = persist(scored)        # no new scores here
    return emit(saved)              # final shape only

# Each module forbids the others' jobs.
# Structure is the optimization, not a label.
# Package: examples/python-tree-of-life-pipeline/

What the map optimizes (stage contracts):

Stage Symbolic Allowed Forbidden
intent kether Validate goals / limits I/O, scoring
intake chokmah Pull raw records Scoring, persist
analyze hod Score / filter File I/O, emission
store yesod Persist New scoring rules
output malkuth Final payload shape Intake, analysis

Measurable before → after (examples/benchmark-tree-of-life/):

Metric Before (flat tangle) After (map stages)
Happy-path parity Same payload for demo-source / max_items=8
Map quality (STRONG×3 + ADEQUATE×2…) ~8 (0 STRONG) ~17 (5 STRONG)
Nodes in import cycles 3 0
Mixed-responsibility files 4 1 (orchestrator only)
Empty source Still runs intake+score Rejects at intent (~30× cheaper)

We do not claim domain scoring is generally CPU-faster. Structure wins on map quality, graph hygiene, mix, and fail-closed control flow. Re-run: python3 examples/benchmark-tree-of-life/harness.py

1) Emit the dual-named layout (Hermes: emit):

python3 scripts/orchestra.py structure \
  -f tree-of-life \
  -c "intent,intake,analyze,store,output" \
  --out ./myapp-skel

2) Implement logic under each stage’s contract (this repo ships a full example):

cd examples/python-tree-of-life-pipeline
python3 pipeline.py

3) Measure structure improvement (parity + map + cycles + mix + early-exit):

python3 examples/benchmark-tree-of-life/harness.py

4) Optional — re-check the graph (Hermes: repo):

python3 scripts/orchestra.py analyze \
  --path examples/python-tree-of-life-pipeline \
  -f tree-of-life --out /tmp/orch-py-best

Flow the code is optimized to follow:

flowchart LR
  intent["intent · kether"] --> intake["intake · chokmah"]
  intake --> analyze["analyze · hod"]
  analyze --> store["store · yesod"]
  store --> output["output · malkuth"]

Scaffold stubs alone are not the product. Orchestra’s value is when implementation obeys the map: one locus per package, one-way edges, fail-closed boundaries. That is optimization by structure — not inheritance of folder names.

Hermes routing (same as CLI)

Inside Hermes, agents must pick a CommandRouter group first, then a command — not freehand architecture. Groups match scripts/orchestra_router.py and SKILL.md.

GroupWhenCommands
meta Integrity, discovery check, list
emit Greenfield skeleton / diagrams from a framework structure, project, diagram
repo Existing tree observe → map → plan → gated moves analyze, optimize

After install, Hermes loads ~/.hermes/skills/orchestra/SKILL.md. Prefer one group per turn; never invent symbolic loci outside schemas/frameworks.v1.json.

Day-to-day commands

# meta
python3 scripts/orchestra.py check
python3 scripts/orchestra.py list

# emit
python3 scripts/orchestra.py structure -f tree-of-life -c "intent,synthesis,output" --out /tmp/orch-skel
python3 scripts/orchestra.py diagram -f numogram --out /tmp/orch-diag

# repo
python3 scripts/orchestra.py analyze --path /path/to/pkg -f tree-of-life --out /tmp/orch-an
python3 scripts/orchestra.py optimize --from /tmp/orch-an/analysis.json --out /tmp/orch-plan
python3 scripts/orchestra.py optimize --from /tmp/orch-an/analysis.json --apply --confirm

Mapping strengths: STRONG ADEQUATE WEAK FORCED — weak/forced fail closed so agents do not paper over bad fits.
